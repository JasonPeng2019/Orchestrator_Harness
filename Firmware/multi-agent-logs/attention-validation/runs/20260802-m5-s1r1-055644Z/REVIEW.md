# M5 S1R1 Post-Attempt Review

**Epoch:** `20260802-m5-s1r1-055644Z`  
**Scope:** read-only review of the retained sprint, harness, watcher, and worker-attention evidence. Worker Codex transcripts were not read. This review is advisory; it does not set disposition.

## Findings

1. **The attempt is not isolated and cannot count.** `ISOLATION.json` explicitly records `valid: false` because the root directly probed manager-signal paths while the attempt was active. M5 permits request discovery only through the blocking `orchestrator_harness watch --until-actionable` path. This is a procedure/fidelity failure, not evidence that the harness woke or failed to wake the manager.
   - **Smallest correction:** preserve this attempt as `RESET` evidence and rerun from a fresh epoch without any direct signal-path probe. No code change is justified by this finding.

2. **The managed harness crashed and the remainder of the attempt was not a continuous native-harness run.** The retained evidence shows the initial managed owner/child recorded in `PROCESS_REGISTRY.json` (PIDs `181884`/`196308`, started 06:07:08Z) differ from `managed-watch-runtime.json` (`owner_pid` `158928`, `watcher_pid` `178728`, started 06:07:09Z). The original foreground invocation was killed by the tool-call timeout. Its attempted restart then failed closed: `stderr.log` reports `prior committed scan process identity changed`. The runtime never records a normal exit (`exit_reason`/`exited_utc` remain null despite `stop_requested: true`).
   - This is both a harness lifecycle interruption and incomplete/contradictory process identity evidence. The fail-closed restart rejection is safety-preserving behavior; it is **not** by itself a reason to weaken the identity check.
   - **Smallest correction:** fix the *manual operating procedure* before retrying: launch the documented native `watch --managed` command directly in a form whose command lifetime cannot be cut off by a short tool timeout, record the actual owner/child identities after it starts, and stop rather than restart it if it is interrupted. Do not add a runner, wrapper, retry mechanism, or change the fail-closed scan-identity behavior.

3. **The diagnostic watcher ran in no-evaluator mode and shut down cleanly, but its configured coverage was not error-free.** `watcher/service.json` shows `evaluator_enabled: false`, `startup_status: READY`, and clean `stop-requested` termination. This supports the required diagnostic-only/no-AI property. However, `watcher/events.jsonl` contains **473 `ROUTE_REJECTED` events**: 464 `malformed json record` rejections plus 8 `json record is not an object` rejections from the four pretty-printed `*_controller.status.json` files, and one malformed record from harness `events.jsonl`. The watcher report nevertheless says `cursor_drained: true`; draining does not make rejected source records healthy.
   - **Smallest correction:** before the next counted epoch, stop listing ordinary JSON controller-status files as JSONL observed sources, or add a narrowly tested native watcher JSON-document source mode if those files are genuinely required for M5 diagnostics. The existing `lane-events.jsonl`, harness attention log, and explicit worker attention inputs should be used for attention evidence. Decide this from the watcher contract; do not paper over rejects or add an external parser/relay. Separately determine whether the single harness-file malformed record is an expected concurrent-tail partial record; if it is not, repair/validate native stable reading before retrying.

4. **Only Atlas has a complete harness wake chain; the other worker records are insufficient, so the required three genuine challenges do not exist.** The watcher report gives Atlas a complete wake ID `ae1fb4c4-…`, including observed/attempted/delivered/received/claimed evidence. It records Boreal and Cygnus as `INSUFFICIENT_EVIDENCE` with missing canonical manager-availability evidence; Delta has contradictory `response_deadline_utc` values. The native harness attention log itself records one actionable wake only—Atlas. Therefore this attempt cannot establish the M5 waiting-manager or busy-manager conclusions even apart from findings 1–3.
   - **Smallest correction:** after the preceding fidelity/config corrections, use the prescribed blocking native wait for every actual challenge and preserve the six-stage records. Do not fabricate or manually probe requests to make a count.

5. **Freeze integrity and post-attempt process cleanup otherwise look good.** The Python source fingerprint has 112 files and matches before/after (`73b4…bfe`); sealed inputs all match; the process registry reports no remaining recorded process and `exact_cleanup: true`. The quiet control is valid (`WATCH_TIMEOUT`, no wake). These facts do not cure the active-attempt isolation, lifecycle, and watcher-coverage failures above.

## Recommendation

Then run a new epoch using only direct native commands, with a long-lived managed harness invocation that is not subject to an accidental short tool-call timeout. Do not add any support process, runner, wrapper, relay, or mid-sprint repair.
