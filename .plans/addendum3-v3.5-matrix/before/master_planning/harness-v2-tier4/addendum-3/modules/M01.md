# M01 - Prerequisite and Admission Closure

## Module contract and selection

| Module type | Decision | Instance IDs | Reason |
|---|---|---|---|
| M01 | SELECTED | MI-NORMAL-ADMISSION, MI-FL2-S1-ADMISSION-PATCH, MI-FL2-S2-ADMISSION-RECONCILE | Role resolution, accepted-baseline truth, the tweak requirement inventory, BOUND-009 through BOUND-019 interpretations, and execution authority must close before frozen-harness launches; STEP-001 also needs scoped correction and checkpoint re-entry without a full admission replay |

## Public interface and compatibility boundary

Consumes one named downstream precondition and its authoritative current state; publishes SATISFIED, MISSING, or INDETERMINATE with the exact consumer. Product behavior is outside this interface. A change to prerequisite meaning, owner, or consumer invalidates the interface.

## Rules, process, recipe actions, and allowed variations

P01, P02, P09, P10, P13, and P14 apply. M01 may perform only an explicitly authorized prerequisite and must independently read it back. It cannot absorb product work or infer user assignment.

| Order | Recipe action ID | Project-specific action/process | Allowed parameterization | Decision owner |
|---|---|---|---|---|
| 1 | M01-A1 | Re-read each STEP-002 and STEP-003 launch prerequisite, SRC-009 gap row, BOUND-009 through BOUND-019 interpretation, and BOUND-013 workspace rule | Exact role, revision, remaining-scope, runtime, command-policy, path, and authority predicates | ROOT |
| 2 | M01-A2 | Observe each predicate without mutation and classify it SATISFIED, MISSING, or INDETERMINATE | One classification per consumed predicate | ROOT |
| 3 | M01-A3 | When all predicates are satisfied, publish admission and stop prerequisite work | No setup repetition | ROOT |
| 4 | M01-A4 | When a predicate is missing and the named owner authorizes action, perform only that prerequisite | User role selection or exact authorized setup only | ROOT |
| 5 | M01-A5 | Read back the resulting role, source, runtime, or authority state independently | Direct source and runtime reads | ROOT |
| 6 | M01-A6 | Publish the prerequisite result consumed by both build steps | Retain only consumed facts | ROOT |
| 7 | M01-A7 | For indeterminate or unauthorized state, publish INCOMPLETE with exact fact and owner | No product fallback | ROOT |

#### Outputs and results

One SATISFIED admission contract or exact MISSING or INDETERMINATE prerequisite. It is retained only until all consuming launches are bound.

#### Concurrency and isolation

ROOT preliminary readback precedes the evidence-lane allocation; terminal evidence precedes construction lanes. Admission has no mutable product root.

#### Resources and side effects

Read-only until the user supplies launch selections or authority. Any user-authored selection is read back; no code side effect is allowed.

#### Checks and acceptance

ROOT compares role keys, Git state, runtime capability, command policy, and explicit authority. GATE-ADMISSION accepts only complete agreement.

#### Failure and exception routes

A correctable prerequisite stays in M01 only after its owner supplies it. Product work or new authority returns to plan/user. No exception route exists.

#### Prior results and change effects

Reuse each observation while its source remains unchanged. A changed repository, runtime, role set, or user direction invalidates only that observation.

#### Repeat, join, and terminal behavior

Recheck from the first unresolved prerequisite. SATISFIED fans out to STEP-002 and STEP-003; INCOMPLETE blocks only consuming launches.

#### Cost and critical-path effect

One short CHECKER evidence launch followed by one ROOT decision is serial because every execution action consumes its output.
