# BEHAVIOR-02 - A real APC child produces a ROOT-reviewable proposal

## Dictated outcome and source

An eligible near-match template may become a bounded proposed plan only through a
real drafting child owned by the candidate product harness and the run's explicit
`apc_adaptation_binding`. Direct fill and ordinary fresh planning remain available;
none of the three branches grants execution authority before ROOT accepts an
exact plan revision. Feature Sections 6.2-6.4 and binding Implementation Section
6.1 govern this outcome.

## Actors, triggers, and preconditions

ROOT requests ordinary planning when no existing same-objective accepted,
candidate, or reviewed plan should continue. Only an explicit ROOT replan
returns an existing candidate/reviewed plan to template/APC selection.
The accepted template shortlist, trusted current field evidence, remaining
absolute stage budget, allowed route, and resolved APC/template controls are
available. Light adaptation requires a complete supported explicit binding
designated lower-capability for that run; missing or invalid binding is a
fallback condition, not a default-model choice.

## Behavioral flow and decision rules

1. Preserve the existing five local families, comparable sanitized scoring,
   lower-ranked eligible candidates, typed direct-fill constraints, and fresh
   fallback. Direct fill changes only declared trusted fields and launches no
   child; historical values do not become current facts.
2. For one eligible near match, ROOT authorizes a bounded drafting-support task
   identifying the parent decision/objective, immutable template revision and
   draft, trusted bindings, allowed edit set, output contract, and remaining
   absolute deadline.
3. The product harness resolves the exact supplied binding and owns launch
   intent, actual child invocation, native corrections, result collection,
   cancellation, review, and cleanup. No outer implementation harness, direct
   provider API, EverOS adaptation client, or inherited lightweight role
   substitutes for that child.
4. The child may read the scoped inputs and return only the declared proposed
   plan. It cannot implement the parent task, accept its own proposal, approve or
   publish memory, start recursive search/APC, launch another child, or claim a
   parent execution result.
5. Before ROOT sees the proposal, validate exact parent/template identity,
   binding, field types, allowed edits, immutable structure/invariants, output
   bound, actual child result, and cleanup state. Queueing through validation and
   cleanup shares one stage deadline; corrections do not renew it.
6. No or incomparable match, missing current fact, unavailable binding, unsafe
   launch ambiguity, timeout, invalid result, exhausted optional budget, or ROOT
   rejection takes normal fresh planning without hiding the attempted reuse.
   ROOT may revise and accept a distinct exact plan revision under the normal
   review rules.

## State, data, and observable effects

The attempted branch, source template, parent decision, requested/resolved/native
binding, child launch/result/cleanup identities, usage when observed, proposal
revision, and final accepted/executed plan source remain distinguishable. Child
completion is not parent acceptance or a second successful coding outcome.

## Edge, failure, and recovery behavior

A lost child-launch acknowledgement is reconciled by exact harness identity
before another launch. If ownership or cleanup is unresolved, conflicting
resource reuse remains blocked and visible while ordinary fresh planning may
continue when safe. Output that invents authorization or current facts, removes
invariants, changes forbidden order, exceeds edits, or claims acceptance is
rejected as a whole, not partly salvaged. Optional APC failure does not invalidate
the exact task or an already accepted plan.

## Constraints and preserved behavior

The accepted APC request/result contract, template library, shortlist, privacy,
and product-harness lifecycle remain compatible. Product deployment selects its
own supported roles; development role names are not hard-coded product defaults.

## Acceptance scenarios

- A valid high match direct-fills only trusted declared fields without a child;
  an incompatible top candidate does not hide a lower eligible one.
- A near match launches one real candidate-harness child through an explicit
  binding, returns a bounded valid proposal with native identity/usage, and waits
  for ROOT acceptance.
- Two supported explicit lower-capability binding configurations can be selected
  without source edits; neither becomes a named or inherited default.
- Missing/invalid binding, deadline, unsafe acknowledgement, invalid edits, or
  child failure produces fresh planning without a direct-call shortcut, leaked
  child, or false parent outcome.
- ROOT rejection records attempted reuse and terminal fresh planning; ROOT
  revision is accepted only under its new exact identity.

## Implementation freedom and unresolved decisions

The narrow harness adapter and proposal encoding are implementation choices.
No product decision remains unresolved.
