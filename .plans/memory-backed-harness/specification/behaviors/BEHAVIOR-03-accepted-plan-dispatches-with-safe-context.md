# BEHAVIOR-03 - An accepted plan dispatches once with safe exact context

## Dictated outcome and source

Only a ROOT-accepted plan for the exact task, objective, route, and execution
baseline becomes worker context and one product-harness dispatch. Mandatory state
remains intact, optional material retains its evidence or guidance role, and a
lost launch acknowledgement never permits blind duplication. Feature Sections
2, 10, and 13 and binding Implementation Section 2.4 govern this outcome.

## Actors, triggers, and preconditions

ROOT has an accepted exact plan from a preserved current plan, direct fill,
adaptation, revision, or fresh planning. The task card, decision, intended
repository/worktree base, checkpoint, remaining work, selected optional memory,
resolved configuration, context allowance, execution role, and product-harness
launch target are known. An APC drafting child never receives this parent
execution envelope. Ordinary legacy task cards remain supported.

## Behavioral flow and decision rules

1. Validate task/objective/decision, exact plan revision and acceptance,
   route, base/worktree, and configuration against the actual dispatch target.
   A proposal or wrong-task packet is non-dispatchable.
2. Recheck plan-affecting procedure eligibility and live or declared-frozen
   freshness within its bounded allowance. Omit an ineligible unrelated item;
   return a plan-dependent change to ROOT.
3. Render mandatory task/constraints and accepted plan/checkpoint before
   optional history and approved procedures. Historical instruction-like text
   remains labeled evidence, never promoted to procedural authority.
4. Pack optional items within their allowance as coherent units. Never shorten
   mandatory task/plan meaning to make room; a mandatory overflow uses ROOT's
   established compaction/recovery route or fails preparation. An approved
   procedure may use a separately approved compact representation, not arbitrary
   truncation or semantic redaction under the old approval.
5. Apply privacy and recipient checks to rendered and remote-bound content.
   Remove product control-plane credentials and mutation authority from worker
   prompt, environment, tools, and configuration. A required task credential
   uses a validated task-only channel or blocks that dependent action.
6. Bind the finalized envelope to actual task, objective, decision, accepted
   plan/integrity, base, rendered content and omissions, role, configuration,
   and invocation target. Bootstrap and native resume validate equivalent
   meaning. Persist launch intent before asking the existing harness to launch;
   observe the actual invocation and reconcile ambiguity before retry.

## State, data, and observable effects

The envelope records selected, packed, omitted, and actually delivered items
with provenance and role. A content or mandatory-identity change yields a new
integrity value and delivery trace. Finalized, intent-recorded, observed,
ambiguous, abandoned, and reconciled states remain distinct; finalization alone
is not evidence that a worker launched.

## Edge, failure, and recovery behavior

A copied but internally valid envelope bound to another task/base fails at the
launch seam. A stale optional item may be omitted with a corrected trace without
rerunning search; a plan-dependent stale item returns to ROOT. Prohibited
mandatory control credentials block dispatch without rewriting the task.
Uncertain live invocation identity blocks duplicate launch until exact
reconciliation. An abandoned pre-dispatch decision never receives an outcome.

## Constraints and preserved behavior

The existing product harness remains sole launcher, reviewer, resume, and cleanup
owner. Optional memory does not alter its ordinary correction/result lifecycle.
All-off and legacy task cards continue the inherited path without optional
context. Same-user processes are not advertised as a hardened sandbox.

## Acceptance scenarios

- An exact accepted plan survives finalize/bootstrap/resume with the same task,
  objective, base, rendered payload, and configuration; a draft, stale plan,
  changed payload, or copied wrong-task envelope fails before launch.
- Historical instruction-like text remains evidence; approved guidance appears
  only in its authorized role. Optional overflow omits whole items while
  mandatory state remains complete.
- Known secrets and control credentials do not reach worker prompt/environment
  or diagnostics; an absent safe task-only channel blocks its dependent action.
- Final freshness drops an unrelated stale item with a new delivery trace, but
  returns a plan-dependent change to ROOT.
- A normal launch has intent and one observed invocation. A lost acknowledgement
  remains ambiguous and no second worker launches before reconciliation.
- All-off and an ordinary legacy task card still use the inherited harness path.

## Implementation freedom and unresolved decisions

Envelope storage, rendering layout, context estimator, and the smallest harness
seam are implementation choices. No product decision remains unresolved.
