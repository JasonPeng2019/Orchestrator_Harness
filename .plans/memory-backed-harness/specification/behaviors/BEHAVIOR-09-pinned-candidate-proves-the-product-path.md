# BEHAVIOR-09 - One pinned candidate proves the integrated product path

## Dictated outcome and source

Development verification proves the fixed-strategy product on one pinned
candidate through relevant local checks, actual scoped Atlas Vector Search,
and a nested native run in which the candidate product harness owns its
workers, APC child, review, and cleanup. Fixture-only or outer-harness-only
activity cannot prove a boundary it did not exercise. Feature Section 16.1
and binding Implementation Sections 1.1-1.2, 15, and 18 govern this outcome.

## Actors, triggers, and preconditions

The implementation owner pins candidate source/install input, an explicit
supported APC binding for the native development wave, current development role
map, network profile, isolated roots, child capacity, and cleanup ownership.
The enhanced task additionally needs an Atlas namespace/index; its absence does
not block the inner all-off task. A focused local all-off check may run without
the APC binding, but cannot replace the mandated bound native wave. The outer
implementation harness delegates a product-test ROOT with authority only for
an isolated instance. That ROOT invokes the recorded candidate product
harness, which launches its own test workers, APC child, and consequential
closeout reviewer. Development roles come from
`.plans/SUBAGENT_ROLE_MODEL_MAPPING.json`; deployed roles remain independent.

## Behavioral flow and decision rules

1. Preflight candidate entrypoint/build, local install, bindings, provider and
   Atlas availability, disjoint outer/inner resources, network profile, nested
   capacity, declared local/remote fixture inputs, and exact cleanup path.
   Drain, pause, exclude, or explicitly control pre-existing jobs that could
   mutate those inputs; do not import outer-harness memory, approvals, worktrees,
   or earlier test results as undeclared product inputs. Missing readiness
   stops only the affected live or native operation; no model substitution or
   unsafe launch is inferred.
2. Run the complete relevant local product and affected harness checks on the
   pinned candidate. Verify isolated package install when packaging or runtime
   dependency inputs changed. Reuse unchanged evidence only when its consumed
   candidate and environment inputs remain the same.
3. Use disposable synthetic Atlas data to observe real Vector Search, exact
   eligibility, and post-change/revocation rejection. Keep an eligible fixture
   only through the dependent native campaign, then clean the owned partition;
   if that campaign cannot proceed, the owner still resolves cleanup.
4. The outer harness launches one product-test ROOT. That ROOT creates an
   isolated candidate instance and runs an ordinary all-off task and an
   enhanced task through the candidate harness. The enhanced task connects
   exact state, reviewed EverOS and eligible Atlas memory, template/APC or
   fresh fallback, ROOT plan acceptance, finalized context, actual worker
   dispatch, terminal review, outcome, effect/usage reconciliation,
   restart/resume, snapshot/isolation, and owned cleanup.
5. At least one near match launches a real product-harness APC child through
   the run's explicit binding. Delegated test ROOT also exercises mapped
   routine, selected middle, and heavy worker tiers on their prescribed
   synthetic assignments, with separate consequential closeout review. Retain
   actual requested/resolved/native role, model, effort, result, usage, and
   cleanup evidence. Deterministic local
   checks may prove direct fill, invalid/missing binding, and timeout fallback;
   they do not become false native-success claims.
6. Product-test ROOT reviews and retires its inner children and returns actual
   evidence. On failure, expose and reconcile the exact owned subtree before
   outer closeout. A product fix produces a new pinned candidate and only the
   affected reruns; no candidate source changes inside a wave.

## State, data, and observable effects

Evidence identifies the outer delegation, test ROOT, candidate build and
entrypoint, inner instance/task/run/worker/APC/reviewer, requested and actual
bindings, results, review/acceptance, outcomes, usage, Atlas partition, and
cleanup. Local, live-service, and native claims remain separate. Ordinary
deployment records do not require outer-test lineage.

## Edge, failure, and recovery behavior

A provider or Atlas outage leaves its dependent claim unresolved, not passing;
unaffected local evidence remains valid. A fallback caused by missing APC
binding proves fallback, not successful adaptation. A raw provider CLI,
implementation-harness worker, narrated test, or mock-only path cannot be
labeled candidate product-harness evidence. Failure cleanup never targets
unrelated processes or roots.

## Constraints and preserved behavior

Only source tests and purpose-built synthetic/disposable coding tasks run now.
No benchmark task/subset/comparison, learned-selector code, or automatically
scheduled follow-up enters the wave. The frozen outer dogfood harness and
`references/harness-single` remain unchanged absent a reproduced run-blocking
defect. Credentials remain outside task cards, prompts, and artifacts.

## Acceptance scenarios

- The pinned candidate's complete relevant local suite and affected harness
  suite report actual results and honest optional skips; its supported package
  installs and imports in isolation.
- Disposable Atlas work observes real Vector Search, exact eligibility, stale
  rejection, and exact owned cleanup after its final dependent use.
- The outer harness launches product-test ROOT, which invokes the recorded
  candidate harness; inner all-off and enhanced synthetic tasks complete
  through that harness's real lifecycle.
- One real near-match APC child runs through the explicit binding, returns a
  valid proposal and usage, and is cleaned; ROOT accepts the parent separately.
- Actual routine, middle, heavy, and reviewer receipts and the APC binding match
  resolved configuration without silent substitution; declared fixture inputs
  exclude uncontrolled prior work, and failure/restart/snapshot cases preserve
  ownership.
- Closeout distinguishes incomplete local/live/native claims and states
  `benchmark execution: deferred/not run` and
  `learned selector: deferred/not implemented`.

## Implementation freedom and unresolved decisions

Synthetic fixtures, grouping of checks, and evidence storage layout are
implementation choices. Live credentials and provider availability are
readiness uncertainties, not product decisions.
