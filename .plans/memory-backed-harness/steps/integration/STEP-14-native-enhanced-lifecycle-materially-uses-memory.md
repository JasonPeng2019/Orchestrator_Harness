# STEP-14 - Native enhanced lifecycle materially uses memory

## Outcome

Master runs one valid Standard task through the actual STEP-12 candidate product
harness. The inner worker consumes the STEP-02 EverOS stored skill and STEP-13
Atlas procedure from its finalized context, materially uses both markers, a
separate reviewer makes the consequential decision, and one durable terminal
outcome records the exact run.

## Scope and touchpoints

Use an isolated inner manager/runtime/worktree and the product's existing
launcher/controller/reviewer. The outer dogfood harness may delegate one
product-test ROOT but is not behavioral evidence. Use the current explicit
provider binding; no APC child is required by this Standard route. Do not change
candidate source during the campaign.

## Implementation

Create a fresh caller-owned temporary EverOS root/store inside the isolated inner
campaign and invoke STEP-01's reusable helper to stage the authentic stored-skill
lineage; then expose/query it through STEP-02's public-surface path. Construct one
exact task/card/accepted plan whose source references require the EverOS and
Atlas marker-directed guidance. Configure the existing product handoff to use
that isolated EverOS root and STEP-13 manifest/receiver/query.
Prepare/finalize on the pinned candidate, read back both selected IDs/digests/
markers, and launch once through the product harness. Require the worker's
machine-readable result to echo or perform both distinct marker instructions.
Run the separate consequential reviewer and record the native terminal outcome
through the accepted path. Capture existing minimal requested/resolved/native
attribution; do not add full usage or extra tier campaigns.

## Dependencies and integration

Consumes STEP-01/02's reusable staging/query path, STEP-12's pin, STEP-13's live
fixture/manifest, and STEP-09–11 native seams. Produces the exact EverOS root,
lane/run/process/terminal identities STEP-15 cleans and the final native behavior
evidence.

## Requirement-fit validation

The proof must observe actual inner candidate launch, both trusted source
identities in durable final context, both marker effects in the worker result,
a distinct review, and the exact durable outcome. A narrative assertion,
outer-worker result, local fake, or launch receipt without material use fails.

**Time-crunch repair gate:** repair only a reproduced normal enhanced lifecycle
defect, used ordinary recovery/compatibility failure, or critical privacy,
identity, trust, duplicate-launch, fabricated-success, durability, or cleanup
invariant. Document extra tier, exhaustive recovery, cosmetic, theoretical, and
non-normal findings without correction, blocking, or re-review. Missing provider
readiness leaves only native proof open.

### Fast test suite

Rerun only STEP-07 and STEP-09–11 focused selectors if their inputs changed after
STEP-12. The decisive check is this single bounded native task; do not add a
second enhanced task, separate full native all-off campaign, or benchmark.

## Failure scope and recovery

On ambiguous launch, stop replay and reconcile the exact inner lane/run/process
identity. Preserve a valid worker result if only review/outcome failed. STEP-15
always retires any created ownership; STEP-13's fixture remains until then.

### Authorized time-crunch staging recovery

If staging fails before any lane record, run ID, process, lease, or worker launch
exists, Master may preserve STEP-13 and perform one controlled local restage.
First prove the failed bootstrap rolled back its child branch/worktree, the
epoch's active-lane list is empty, and the exact outer staging worktree is
unregistered. Preserve the failed intent and inner directory as attempt-1
evidence; use a distinct retry inner directory and a fresh caller-owned EverOS
root. Add a nonsecret bootstrap-result breadcrumb before retry so a second
failure is diagnosable. Reuse the unchanged validated Atlas manifest/collection;
do not republish Atlas and do not launch more than one worker. Any ambiguous
lane/process/launch evidence forbids restaging and transfers directly to
STEP-15 reconciliation.

### Fast lane for revisiting old work

Resume at the first unresolved native boundary—preparation, launch observation,
material-use result, review, or outcome—retain all earlier exact evidence, and
rerun only the invalidated observation after a reviewed code repair.
