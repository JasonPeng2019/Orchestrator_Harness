# STEP-13-2 — Match network claims to launched tools

This step is a derivative of [original STEP-13](../../source-steps/STEP-13-network-modes-are-enforced.md).

Owner: lane 2. This is the complete launched-payload network assignment.

Apply lane 1's resolved network profile to the actual STEP-12 installed and launched provider/tool payload. In soft mode suppress supported provider-native general web/fetch/search tools while disclosing shell egress that remains possible. Atlas-only may be claimed only with measured independent unrelated-destination blocking and installed-payload verification; otherwise report the downgraded effective profile. Do not describe same-user process configuration as a hardened sandbox.

Evidence: inspect installed tool settings and actual launched payload, test suppression and truthful downgrade, and pass effective enforcement-source facts to STEP-15-2.

Consume the per-objective requested/effective profile and captured configuration. In `soft_guardrail_network`, suppress supported provider-native general web/fetch/search tools while explicitly disclosing any unsuppressed shell egress. In `atlas_memory_only`, claim isolation only after independent unrelated-destination blocking is measured and the actual installed/launch payload is verified; otherwise downgrade the effective claim. In `restricted_local`, do not pass a payload that re-enables optional Atlas task-path access. Feature Spec Section 15 off-state remains an independent gate. Do not describe same-user process flags as a hardened sandbox or a service outage as a permission decision. Exercise installed tool settings, actual launched payload, soft suppression, Atlas-only downgrade, and forbidden-call counts with affected harness/provider tests. If egress proof is absent, block only the stronger claim or affected task.

For a revisit, repair only the installed tool setting or launched-payload gate and rerun direct payload/forbidden-call checks. Revisit STEP-15/17/18 only where the changed effective profile was consumed.
