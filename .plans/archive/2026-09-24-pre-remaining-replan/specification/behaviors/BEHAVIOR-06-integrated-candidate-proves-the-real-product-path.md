# BEHAVIOR-06 - A pinned candidate proves the real integrated product path

## Dictated outcome and source

Development verification establishes the complete fixed-strategy product on one
pinned candidate through its authoritative local checks, an actual scoped Atlas
Vector Search lifecycle, and the required nested native test in which the
candidate product harness owns its workers and APC child. Fixture-only or outer-
harness-only activity cannot stand in for the boundary it does not exercise.
Feature Section 16.1 and Implementation Sections 1.1–1.2, 15, and 18 dictate this
development outcome.

## Actors, triggers, and preconditions

The implementation owner freezes a candidate build/source manifest, installed
entrypoint, local and remote test identities, role mapping, selected middleweight
alternative where applicable, explicit APC binding, network profile, provider and
service availability, child capacity, and cleanup contract. The outer
implementation harness launches a delegated product-test ROOT. That ROOT sets up
and invokes the isolated candidate product harness, which launches its own test
workers, APC child, and consequential closeout reviewer.

The current development role bindings are resolved from
`.plans/SUBAGENT_ROLE_MODEL_MAPPING.json` immediately before launch. They are
test configuration, not deployed product defaults. APC independently uses the
run's explicit `apc_adaptation_binding`.

## Behavioral flow and decision rules

1. Preflight the pinned candidate, package/install path, local roots, isolated
   worktrees/queues/leases/evidence, provider role and APC bindings, network mode,
   Atlas namespace/index, nested child capacity, and exact cleanup ownership.
   Missing required readiness fails before the affected native launch rather than
   substituting a binding or risking parent/child deadlock.
2. Run the complete relevant local product suite and affected harness suite on the
   pinned candidate. Build and install the final package in an isolated supported
   Python environment when packaging or runtime dependency inputs changed.
3. Exercise actual Atlas Vector Search using synthetic, uniquely scoped data:
   publish/discover, exact-read and eligibility-check, change current or revoke,
   prove stale delivery is blocked, and clean only owned resources. A retained
   earlier live result is reusable only when every consumed adapter,
   representation, lifecycle, dependency, and service input is unchanged.
4. The outer harness delegates one product-test ROOT. Product-test ROOT launches
   the recorded candidate product harness with disjoint runtime directories,
   worktrees, state stores, Atlas partition, processes, and ownership from the
   outer run.
5. Through that candidate harness, complete one ordinary all-off synthetic task and
   one enhanced synthetic task. The enhanced path connects exact state, reviewed
   EverOS evidence, an eligible Atlas procedure, template/APC or fallback planning,
   ROOT acceptance, finalized context, real worker dispatch, terminal review,
   exact outcome, side-effect/usage reconciliation, restart/resume, snapshot or
   isolation behavior, and cleanup.
6. The enhanced path performs at least one real near-match APC launch through the
   selected explicit binding. Actual requested/resolved/native role and effort
   evidence is retained for the development roles and APC. Silent substitutions
   fail the affected native claim. Deterministic configuration checks can prove a
   second supported APC binding is selectable without requiring a second native
   model run unless that binding itself is claimed as natively exercised.
7. Product-test ROOT drains, reviews, retires, and archives its inner children and
   returns the product evidence to the implementation owner. On failure, it exposes
   the recorded owned subtree for exact reconciliation. The outer owner then closes
   only the outer lane.

No candidate product source changes during one wave. A product defect returns to
its owning behavior for repair and produces a newly identified candidate and only
the affected reruns.

## State, data, and observable effects

Native evidence identifies the outer delegation, product-test ROOT, exact candidate
entrypoint/build, inner product instance, task/run/worker/APC/reviewer identities,
requested and resolved bindings, actual results, linked review/acceptance,
outcomes, usage, Atlas partition, and cleanup. Normal deployment records do not
require the outer test lineage.

Local, live-service, and native claims remain separate. Unavailable environments
or missing usage are reported as limitations or blockers for their specific claim,
not converted to passing coverage. The invoked workload manifest contains only
source tests and synthetic/disposable tasks.

## Edge, failure, and recovery behavior

- A local regression blocks the behavior it reaches before native launch. A
  provider or Atlas outage leaves the dependent live claim unresolved while
  retaining unaffected local evidence.
- A changed candidate after repair starts a new identified native wave. Reuse
  earlier evidence only where its inputs and downstream path are unchanged.
- Product-test ROOT failure exposes and reconciles its exact inner children before
  outer closeout. Cleanup never enumerates or kills unrelated processes by name.
- An APC fallback caused by missing/invalid binding proves fallback only, not
  successful adaptation. Provider stubs prove launch contracts only, not native
  model coverage.
- Outer implementation activity, a narrated test, or a direct provider CLI call
  cannot be labeled candidate product-harness evidence.
- No failed or successful wave triggers a benchmark, comparative cohort, learned
  policy load/update, or further recursively nested test harness.

## Constraints and preserved behavior

Development-test topology and roles do not become required deployment topology or
model defaults. The frozen outer harness and `references/harness-single` remain
unchanged unless an actual run-blocking defect is reproduced. Test service data is
synthetic and namespace-scoped; credentials stay out of prompts and artifacts.

## Acceptance scenarios

- The pinned candidate's complete local suite and affected harness suite pass with
  actual counts and honest optional skips; an isolated install imports and exposes
  the declared supported operational surface.
- Candidate setup preserves both harness and ROOT-suite capabilities, rejects an
  ownership collision before mutation, recomposes after a simulated upstream
  overwrite, recovers interrupted composition before enhanced dispatch, and
  validates the actual launched worker payload.
- A disposable live Atlas run observes a real Vector Search hit, exact eligibility,
  and post-change or revocation rejection, then cleans its owned namespace.
- The outer harness launches a delegated product-test ROOT, and that ROOT invokes
  the recorded candidate harness rather than the coding harness or raw provider
  CLI.
- The inner all-off task completes with no memory call or context. The enhanced
  task completes the exact state-to-memory/APC-or-fallback-to-accepted-plan-to-
  dispatch-to-outcome-to-reconciliation path with actual Atlas participation.
- The candidate harness launches the selected APC child through the explicit
  binding, validates its proposal and usage, and cleans it; direct fill and
  missing/invalid/timeout paths are established by focused tests without false
  native claims.
- Actual role/model/effort evidence matches the current mapping with no silent
  substitution, while product configuration remains independently deployable.
- Restart, ambiguous-operation, snapshot/isolation, inner failure, and cleanup
  cases preserve exact ownership and leave outer/unrelated resources untouched.
- Inspection of the actual tasks and follow-up work shows no benchmark or learned-
  selector activity; closeout reports both as deferred.

## Implementation freedom and unresolved decisions

Synthetic fixture content, test grouping, evidence storage layout, and exact
provider syntax are implementation choices. Availability of live credentials and
native bindings is a readiness uncertainty, not an unresolved product decision.
