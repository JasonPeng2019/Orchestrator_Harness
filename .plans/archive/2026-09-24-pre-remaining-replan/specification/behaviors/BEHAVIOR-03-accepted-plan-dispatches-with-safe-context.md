# BEHAVIOR-03 - An accepted plan dispatches once with exact safe context

## Dictated outcome and source

Only a ROOT-accepted plan for the exact current task, objective, route, and
repository baseline becomes an execution-worker handoff. The product renders
mandatory state and eligible optional memory with their roles intact, strips
control authority, and dispatches through the existing product harness exactly
once or exposes an unresolved launch. Feature Sections 2, 10, and 13 and
Implementation Sections 2.3–2.4 and 9 dictate this outcome.

## Actors, triggers, and preconditions

ROOT finalizes after accepting an exact plan from preserved current state,
direct-fill, adaptation, revision, or fresh planning. Inputs include the exact
task card, objective and decision, intended base and worktree, accepted plan,
current checkpoint/remaining work, optional selected cases and procedures,
configured context allowance, privacy policy, execution role, and harness
invocation target.

An APC drafting child does not use this parent execution envelope. Legacy task
cards and the all-off path remain valid without optional memory context.

## Behavioral flow and decision rules

1. Validate the task, objective, decision, accepted plan and review/acceptance
   evidence, intended repository/worktree base, route, and configuration against
   the actual dispatch target. A proposal, candidate, or fresh plan that ROOT has
   not accepted cannot dispatch.
2. Recheck plan-affecting optional procedure eligibility and live/frozen freshness
   within the bounded final allowance. A plan-affecting change returns to ROOT;
   ineligible guidance that does not affect the plan is omitted.
3. Render semantically distinct sections for authoritative task/constraints,
   accepted plan/checkpoint and remaining work, historical cases, approved
   optional procedures, and output/review contract. Instruction-like historical
   text remains labeled evidence and cannot move into procedural guidance.
4. Mandatory task and accepted-plan state is outside the optional-memory allowance
   and is never truncated to preserve optional memory. The complete rendered input
   must fit the known usable context. An oversized mandatory packet uses ROOT's
   established compaction/recovery route or fails preparation.
5. Deliver an approved procedure coherently with meaning-preserving references and
   warnings, or omit it. Arbitrary truncation, summary, or redaction cannot change
   approved meaning under the same revision; a separately approved compact
   representation may be used.
6. Apply privacy checks to every rendered or remote-bound value. Remove product
   control-plane credentials and authority from the worker prompt, environment,
   tools, and configuration. A needed task credential uses a validated task-only
   channel; absent such a channel, the credential-dependent action blocks without
   rewriting the user's authoritative task.
7. Bind the final envelope to the exact task card, objective, decision, accepted
   plan and integrity, intended base/worktree, rendered content and omissions,
   execution role, run/invocation target, strategy, and configuration. Bootstrap
   and native resume validate equivalent meaning.
8. Persist dispatch intent before asking the existing harness to launch. Record the
   actual observed harness invocation after launch. If acknowledgement is lost or
   identity is ambiguous, reconcile the existing invocation before any repeat.

## State, data, and observable effects

The finalized envelope records or exactly references all mandatory identities,
the actual rendered mandatory and optional items, each delivered item's origin and
revision, explicit omissions, role separation, configuration, and complete
integrity. Changing any bound field creates a different envelope and delivery
trace.

Dispatch state distinguishes prepared/finalized, intent recorded, observed
invocation, ambiguous, abandoned, and reconciled/delivered facts. A finalized
envelope alone is not a delivery receipt. The worker observes only its final task
context and permitted runtime; ROOT/operator can inspect the exact dispatch and
omission result without exposed secrets.

## Edge, failure, and recovery behavior

- A task, base, plan, decision, run, or worktree mismatch fails before unsafe
  launch even if the copied envelope is internally well formed.
- If one optional item becomes ineligible before dispatch, omit it and regenerate
  exact delivery evidence without rerunning semantic search. If the accepted plan
  depends on it, return the plan to ROOT.
- An oversized optional set is deterministically packed or omitted within its
  allowance. Oversized mandatory state does not get silently shortened.
- A prohibited secret in optional material causes omission or safe replacement. A
  prohibited mandatory control credential blocks until ROOT supplies an authorized
  arrangement; the product does not fabricate a secret manager.
- Lost launch acknowledgement, unreadable invocation identity, or a potentially
  live controller blocks a duplicate launch until exact reconciliation or ROOT
  recovery.
- A pre-dispatch abandoned preparation remains non-dispatchable and cannot later
  receive an execution outcome.

## Constraints and preserved behavior

The existing product harness remains the only launcher, controller, reviewer,
resume owner, and cleanup owner. Optional memory does not change clean-worktree,
result, correction, or provider lifecycle semantics. Legacy task cards without a
memory handoff continue through the ordinary harness path. Same-user processes are
not advertised as a hardened sandbox.

## Acceptance scenarios

- An exact ROOT-accepted plan creates a finalized envelope whose task, objective,
  plan, base, rendered content, and configuration survive bootstrap and resume
  round trips unchanged.
- A proposed or candidate plan, wrong-task packet, wrong base, stale plan revision,
  or changed rendered payload fails before launch.
- Historical text that looks like an instruction remains in the evidence role;
  approved guidance is delivered only in its procedural role.
- Optional context reaches its bound without truncating mandatory task/plan state;
  one coherent skill is omitted rather than cut into misleading fragments.
- A known secret is absent from queries, optional context, prompt, diagnostics,
  and worker environment, while a protected source reference remains usable by
  the authorized owner.
- All-off and a legacy task card run the ordinary harness without initializing an
  optional memory envelope.
- One optional item fails final freshness and is omitted with a new exact delivery
  trace; a plan-dependent failure returns to ROOT instead.
- A normal launch records intent and one observed invocation. A lost acknowledgement
  leaves one ambiguous operation and a retry is refused until that exact execution
  is reconciled.

## Implementation freedom and unresolved decisions

Envelope storage location, prompt rendering layout, token estimator, and the
smallest harness integration seam are implementation choices. The implementation
may extend the accepted handoff contract compatibly or migrate it explicitly. No
product decision remains unresolved.
