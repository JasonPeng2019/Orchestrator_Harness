## 1. Agent-per-role mapping

The writer-manager performs all planning, triage, integration, and final decisions. Production coding is serial. Pool size 1 is the default; size 2 is used only for the high-risk or genuinely disjoint slices named below. No development pool uses all three available worker slots.

| Role | Agent chosen | Pool size | Pool-size authority |
|---|---|---:|---|
| orchestrator / planner-executor | current Codex writer-manager session | 1 | fixed |
| coder-main | GPT-5.6 Luna, high reasoning | 1 | fixed |
| reviewer-main | GPT-5.6 Terra, medium reasoning | 2 | maximum; each step selects 1 or 2 |
| doer-main | GPT-5.6 Luna, high reasoning | 2 | maximum; each step selects 1 or 2 |
| final-reviewer | GPT-5.6 Terra, medium reasoning | 1 | skill |

During practical acceptance, a separate GPT-5.6 Sol subagent orchestrates the candidate harness. All target-project workers and the isolated watcher use GPT-5.6 Luna, medium reasoning. The outside writer-manager never becomes the orchestrator of the system under test.

Concurrency and authority:

- One writer-manager plus at most three subagents may exist at once.
- Planning, production code, shared-file edits, repair, integration, and merge decisions are serial.
- A single review, author, or test lane is valid and has no artificial split.
- Two workers run only for the exact independent slices declared in a large step.
- Green tests remain recorded. Ordinary repair reruns only failing or newly implicated tests.

### Subagent launch and frozen-checkout guardrail

Every subagent launches with `--dangerously-bypass-approvals-and-sandbox` and approval policy `never`, from its assigned candidate, validation, evidence, target, or watcher working directory. No subagent launches from the outer repository or `frozen-harness-to-use`.

- Every worker prompt forbids reading, listing, searching, editing, executing, or otherwise inspecting `frozen-harness-to-use`.
- Worker prompts expose no frozen path except the denylisted checkout name.
- Only the writer-manager deliberately accesses both checkouts.
- Before and after every worker wave, the writer-manager records the frozen checkout's `HEAD`, porcelain status, and binary diff.
- Any difference rejects the entire wave, stops launches, and enters the safe repair boundary. Nothing automatically reverts the change.
- The frozen harness remains the outside observer during development. It is stopped before candidate acceptance.

Skill-decided large-step split map:

| Large step | Review pool | Author pool | Test pool | Why this size |
|---|---:|---:|---:|---|
| S1 General coding worker | 1 | 1 | 2 | one integrated worker-boundary review and one cohesive test author; coding and firmware checks isolate cleanly |
| S2 Git-safe completion | 1 | 1 | 2 | one integrated merge-safety review and one shared-fixture author; Git and result matrices isolate cleanly |
| S3 Coordination and recovery | 2 | 2 | 2 | lock/process safety and event compatibility are distinct; lock and event tests own disjoint files and state |
| S4 General-use delivery | 1 | 2 | 2 | one coherent product-readiness review; documentation smoke and integration tests are disjoint |
| Final review | 1 | 1 | 2 | one fresh contract review and one gap author; two isolated final test groups only when not already green |

Dependency decisions and deliberately serialized boundaries:

- S1 precedes all other product work because it establishes the generic coding contract.
- S2 follows S1 because Git and result identity attach to the coding invocation.
- S3 follows S2 because reconciliation must consume final Git/result facts and lock claims.
- S4 follows S3 because its integration fixture proves the whole stabilized path.
- Automated final review and practical acceptance begin only after S4 pins one candidate commit.
- Baseline, candidate gate, practical acceptance, physical firmware acceptance, and promotion are gates, not large implementation steps.

Only one target worker runs at a time during C3 because the outside writer-manager, candidate orchestrator, and watcher occupy the other three agent slots. The target branches form a descendant chain, so final merge is a verified fast-forward rather than a conflict-heavy multi-branch merge.

- **C0:** Spawn a fresh final-reviewer invocation. Reviewer pool size is 1, so no split occurs.
- **C1:** Give it the final/acceptance spec and exact candidate. One author adds only missing tests; an explicit no-gap record is valid.
- **C2 - final test loop:** Run only tests not already green or invalidated by the final gap commit. D1 and D2 may run in parallel because their state is isolated. One triage and one serialized repair follow any failure; no static review reopens.
- **C3 - practical test:** Stop the frozen harness completely, create fresh candidate and target runtime state, then let F.C3.O use the candidate harness to build the taskboard project. The outside writer-manager does not direct target workers.
- **C4 - nested static-audit loop:** This remains dormant. It is the only post-Checkpoint-A static-review revival and runs only after a repeated harness-shaped practical failure or watcher abort, after the entire C3 topology is stopped. One fresh Terra reviewer audits preserved evidence, the outside writer-manager plans, one Luna-high coder repairs the harness under a fresh frozen epoch, one regression test is added, and automated gates precede a completely fresh C3 target repository.

Watcher rules:

- The watcher has no communication or control edge to F.C3.O or any target worker.
- It cannot edit, acknowledge, repair, advise, or stop an ordinary application or orchestrator failure.
- Its only action is to terminate the exact complete C3 process tree for a demonstrated candidate-harness or watcher defect and notify the outside writer-manager.
- Bad prompts, malformed or stale worker results that the harness rejects, failed tests, retries, merge conflicts, and incorrect orchestrator-maintained auxiliary evidence stay inside the candidate coding flow. A mismatch in an auxiliary manifest is not a harness defect when controller status and native events remain correct.
- No harness repair occurs while the failed candidate topology is live.

## 8. Safeguard

- `final_full_verification`: `true`.
- After practical success and exact candidate shutdown, run the complete accumulated suite exactly once with `uv run --project .codex/dev --locked python .codex/scripts/verify.py --full`.
- A safeguard regression returns only its stable test IDs to the relevant serialized repair and focused loop; the post-repair safeguard then runs once on the new candidate.
- Required synthetic firmware tests are part of the accumulated suite.
- Physical firmware acceptance is release-only: run it only for a public firmware-supporting release or after hardware-specific changes, with exclusive hardware resources and recorded cleanup evidence.
- Completion summary records the exact candidate commit, taskboard commit, practical evidence, full-suite evidence, watcher report, shutdown evidence, and out-of-scope ledger.

## 9. Rules the runner applies

- **Goal:** ship a working product efficiently. Do not add ceremony, agents, review slices, or features merely because capacity exists.
- **Triage:** a broken realistic, non-trivial path is a functional defect and is fixed. Speculative hardening, style-only rigor, hypotheticals, invented complexity, or edge behavior already adequate for roughly 99.9% of real use is extraneous and is recorded then dropped. Reviewer recommends; orchestrator decides.
- **Step granularity:** requirements map to modules; multiple coherent modules map to one large step; the full QA cycle runs once per large step.
- **Pool sizing:** 1 is the default and is as valid as 2 or 3. Increase only for named independent work with a concrete benefit.
- **Singleton direct handoff:** a size-1 pool has no fake split or merge; its result goes directly to triage or integration.
- **Split authority:** only actual multi-worker pools split. The plan fixes their non-overlapping concepts and paths; the runtime never re-partitions them.
- **Merge-then-triage:** every real fan-out rejoins before the writer-manager makes one decision.
- **Production coding:** one serial coder-main completes every module in the current large step.
- **Authoring:** only disjoint test/documentation files may be written concurrently; product and shared fixtures remain single-owner.
- **Passed registry:** each check uses targeted stable test IDs such as `path::class::test`. Green IDs stay locked during ordinary loops.
- **Reruns:** run only still-failing gap tests, failed unit tests, and tests newly implicated by the changed behavior. The final safeguard is the only routine full-suite rerun.
- **Static review:** Checkpoint A closes ordinary review for that large step. Test-loop repairs do not reopen it. Only dormant C4 may revive review after practical failure.
- **Termination:** loops have no iteration cap but stop and report on success, unrecoverable error, `stall_threshold` consecutive no-progress attempts, repeated same-signature failure, pass/fail oscillation without passed-set growth, or only-extraneous scope churn.
- **Current harness:** do not assume a scheduler, task database, automatic launcher, generic lock, coding schema, or result validator exists before its implementing step passes.
- **Live-run discipline:** use fresh epoch state, freeze live code/configuration, wait through the native event path, acknowledge only after handling, and repair only after safe shutdown.
- `scope_policy`: `ship-realistic`.
- `gap_scope`: `change`.
